# 给 AI 点餐项目补一套可复现评测：0.72 → 0.81，和 97.6% 拒答率背后的取舍

做 RAG 项目最容易陷入的状态：demo 能跑、回答看起来像样，但被问一句「效果怎么样」就只剩主观描述。
这篇文章记录我给 [AiMenu](https://github.com/Gunaie/AiMenu) 补评测体系的过程——数据集怎么造、
三组消融怎么设计、拒答阈值踩了哪些坑、Agent 护栏怎么回归，以及最后如何把「指标不许倒退」写进 CI。

完整数据、脚本和失败案例都在仓库里，本文只讲思路与结论。

## 一、先有评测集，再谈优化

最初的评测集只有 153 道菜、几十条查询，Top-3 轻松 0.97。数字很好看，但没有任何说服力：
语料太小、标注太简单，换个问法就崩。

重做时定了三条规则：

1. **语料扩到 1060 道菜**，覆盖家常菜、汤羹、主食、饮品、甜点；
2. **查询按真实用户习惯分层**：名称精确 125 条、口语化 270 条（「那种红亮亮的甜口红烧肉」）、
   近似干扰 95 条（鱼香肉丝 vs 鱼香茄子）、属性约束 95 条（「五十块以内、有牛肉的」）；
3. **单独造 84 条域外负例**：非餐饮 20、业务能力外 14、菜单不存在 17、Prompt 注入 15、
   越权请求 10、无意义输入 8。

第二批数字立刻掉下来：混合检索 Top-3 只有 0.90，属性约束类 Top-1 不到 0.5。
这才是真实起点，也才有优化空间。

## 二、三组对照，而不是只报一个最好看的数

评测脚本固定同一批 585 条标注，只切换检索策略：

| 策略 | Top-1 | Top-3 | MRR |
| --- | --- | --- | --- |
| 纯向量 | 0.7214 | 0.8359 | 0.7729 |
| 向量 + BM25（RRF） | 0.7385 | 0.8735 | 0.8000 |
| + Cross-Encoder 精排 | **0.8120** | **0.9043** | **0.8524** |

结论很直接：BM25 融合只带来 1.7pt，精排带来 7.4pt——**瓶颈在排序，不在召回**。如果只报最后一行的
0.81，读者无法判断钱花在哪，也无法判断换掉重排后会不会更差。

## 三、两个真实的坑

### 坑 1：本地重排模型对输入格式极其敏感

云端重排模型对「菜名 + 价格 + 描述」拼成的长串不敏感，本地 `bge-reranker-v2-m3` 却会被冗余文本稀释，
分数整体塌陷，甚至不如纯向量。

修复方式是把 Rerank 输入归一化：查询剥离「来个」「推荐一下」这类修饰词，候选只保留菜名、价格、
口味、主要食材等核心字段。同一批数据，归一化前后排名质量差异明显。这不是调参，是喂给模型的数据形态问题。

### 坑 2：换 Embedding 必须重标阈值

拒答依赖「最高重排分 < 阈值」。从 v4 切到 v3 之后，向量分布变了，旧的 0.115 明显过松：
84 条域外负例里有 5 条被误收（「红烧熊掌」「杨枝甘露蛋糕」这类像菜但菜单没有的查询）。

重新标定的方法是：按 `seed=42` 把正例与负例各切一半做 dev / test，**只在 dev 上选阈值**，
再报告 test 上的结果：

| 口径 | 阈值 | 正例接受率 | 域外拒答率 |
| --- | --- | --- | --- |
| 旧配置 | 0.115 | 0.9778 | 0.9405 |
| dev | 0.245 | 0.9658 | 0.9762 |
| test（留出） | 0.245 | 0.9352 | 0.9762 |

最终选 0.245：域外拒答从 94.05% 提到 97.62%，代价是正例误拒从 2.2% 升到 6.5%。
这是一个明确的产品取舍，写进 README，而不是藏起来。

更重要的是评测集切分：如果在同一批数据上调完阈值再报指标，97.62% 这个数字就是虚的。
这也是我在项目文档里专门标注「阈值只在 dev 标定」的原因。

## 四、Agent 的护栏也要能回归

RAG 只解决了「找得到」，Agent 还要解决「不闯祸」。65 条端到端用例覆盖检索、价格、加购、下单、
订单查询、配送、拒答与多轮约束，判定指标分得比较细：

- 工具选择准确率 0.9385；
- 约束槽位、约束生效、菜名有效性全部 1.0；
- 拒答准确率 0.8571。

失败用例全部公开在 `data/eval_failure_cases.json`：6 条失败里 4 条是「模型跳过了工具调用」，
2 条是拒答边界。前者正是多轮对话里「只改约束、不重新检索」的典型退化，项目里用强制注入规则 +
迭代上限兜底，但仍然有残余——把失败摊开写，比只报 0.94 更可信。

护栏本身也做了回归：订单工具强制注入 `user_id`（防止漏传导致越权）、服务端重算金额、配送范围
服务端校验、幂等键 + 行锁防重复下单与超卖。这些不是「安全加分项」，而是评测里可复现的断言。

## 五、把「指标不许倒退」写进 CI

只有脚本还不够，指标必须有人守着。仓库里的做法：

1. `data/eval_baseline.json` 保存当前最优基线；
2. `scripts/eval_rag.py --baseline ...` 对比 `recall@k` / `MRR`，跌幅超过 0.02 直接失败；
3. `scripts/check_eval_regression.py` 对比 Agent 的工具、约束、菜名、拒答等指标，
   小样本容忍度放到 0.05；
4. 评测产物与失败案例集作为 artifact 上传，方便复查。

一个容易忽略的前提：**基线必须和 CI 使用同一套配置**（同样的 Embedding、重排器、阈值）。
我在 CI 里显式覆盖了 `.env`，否则「假回退」会天天报警。

## 六、几条可复用的经验

- 评测集要分层，否则平均值会掩盖短板（属性约束类 Top-1 只有 0.49）；
- 只报最优策略没有信息量，必须有纯向量 / 融合 / 精排三组对照；
- 阈值必须在独立 dev 集上选，test 集只用于报告；
- 换模型 = 换阈值，不存在「沿用旧配置」这回事；
- 失败案例要落成结构化数据，而不是散落在文档里的几段话；
- 指标门禁要固定模型快照，别名自动升级会让结果不可复现；
- 护栏指标（越权、金额、库存、拒答）应该和准确率一样进入回归。

## 七、局限

语料是模拟的，标注由单人完成，Agent 只有 65 条用例，Rerank 跑在 CPU 上（P50 约 2.6s）——
这些限制都写在[评测报告](eval_report.md)里。评测不是为了让数字好看，而是为了让「哪里不行」
可以被指出来，并且在下一次改动后仍然被记住。
