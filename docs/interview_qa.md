# AiMenu 项目面试常见问题及答案 (从易到难)

这份文档将帮助你应对面试官针对该项目的全方位“轰炸”。

---

## 一、 基础篇 (适合初级面试/开场白)

**Q1: 简单介绍一下这个项目的架构？**
*   **A**: 这是一个典型的 AI 增强型全栈项目。后端采用 FastAPI 异步框架，通过 LangGraph 管理 AI Agent 的推理流程。存储层使用了 MySQL 处理关系数据，Redis 处理热点缓存，ChromaDB 作为向量数据库支持 RAG 检索。前端使用 Vue 3 提供交互，并通过 Docker 进行中间件编排。

**Q2: 为什么选择 FastAPI 而不是 Flask 或 Django？**
*   **A**: 因为 AI 业务通常涉及大量的 I/O 操作（如调用 LLM API、查询向量库）。FastAPI 原生支持异步（async/await），能够显著提升并发处理能力；同时它自带 Swagger 文档，极大方便了前后端联调。

---

## 二、 进阶篇 (技术细节)

**Q3: 你的 RAG 检索为什么要做“混合检索”？**
*   **A**: 纯向量检索（Semantic Search）虽然能理解意思，但在处理专有名词（如“回锅肉”）时容易失效。通过引入 BM25（关键词检索），我们可以保证精准匹配；最后再通过 Rerank 模型进行重排序，确保最相关的菜品排在最前面。

**Q4: Redis 在本项目中除了做缓存，还解决了什么问题？**
*   **A**: 主要是性能和成本优化。高德地图 API 的调用是有配额且耗时的。我们把地理编码结果缓存 24 小时、距离与地址补全结果缓存 1 小时，短时间内重复查询直接命中 Redis，不再重复调用高德接口。

---

## 三、 深度篇 (架构难点)

**Q5: 解释一下“延迟双删”策略？**
*   **A**: 这是为了保证数据库与 Redis 缓存的一致性。当管理员修改菜品价格时：
    1. 先删除 Redis 缓存。
    2. 更新 MySQL 数据库。
    3. 延迟几百毫秒后再次删除缓存。
    这样可以防止在数据库更新期间，旧的查询请求将过期数据重新写回 Redis。

**Q6: 为什么用 LangGraph 状态机而不是传统的 Sequential Chain？**
*   **A**: 传统的链式结构是线性的，无法回头。LangGraph 允许我们定义“环路”。例如：AI 查到用户地址在配送范围边缘，它可以选择先“反问”用户确认位置，再继续逻辑。这种“决策 -> 执行 -> 反馈 -> 修正”的循环更接近真实的人类逻辑。

---

## 四、 场景与扩展篇 (核心竞争力)

**Q7: 如果 LLM 产生“幻觉”，推荐了菜单上没有的菜怎么办？**
*   **A**: 主要靠三层约束。检索侧用 Rerank 最高分做无答案判定：低于阈值时 `search_menu` 返回 `answerable=false`；System Prompt 要求模型如实说“小店暂时没有这道菜”，可以推荐相近菜品但不能编造；返回给前端的 `menu_ids` 只用于渲染快捷加购，前端按 ID 从菜单里取菜名，取不到时显示“未知菜品”，最终下单金额与菜品仍由服务端按数据库重算。端到端评测里“有帝王蟹吗”这条就是按这个路径如实拒答的。

**Q8: 项目如果面临高并发下单，你会如何优化？**
*   **A**: 
    1. **限流**: 在 FastAPI 层引入 Rate Limiter。
    2. **消息队列**: 将下单后的通知推送、地理轨迹计算等耗时任务丢入 Celery 或 RabbitMQ 异步处理。
    3. **数据库优化**: 引入数据库读写分离，利用 Redis 承载绝大部分的菜单查询压力。

## 💡 面试小贴士：
在回答时，多使用**“实验数据”**。例如：“在 150 条标注上，纯向量 Top-3 Recall 是 0.9733，加 BM25 融合与 Rerank 后是 0.9933；拒答阈值则用 dev/test 切分标定，held-out 误拒 3/75。”这会显得你非常专业且注重工程落地。
